# Productivity OS iOS — QR Authentication Specification

## 1. Purpose

Allow an existing Productivity OS user who is already authenticated on the web application to securely authenticate the iOS app by scanning a QR code.

The goal is to make first-time iOS authentication fast and seamless:

Web
→ Generate QR
→ Scan with iPhone
→ Confirm
→ iOS authenticated
→ Today

This replaces the need to manually enter email/password during the initial iOS login flow.

---

# 2. Authentication Flow

The complete flow:

    Web Productivity OS
            ↓
    Authenticated user
            ↓
    Generate login challenge
            ↓
          QR Code
            ↓
        iPhone Camera
            ↓
       Scan QR challenge
            ↓
      Validate challenge
            ↓
      User confirmation
            ↓
       Backend exchange
            ↓
       Secure iOS session
            ↓
           Today

---

# 3. Security Model

The QR code MUST NOT contain:

- Access token
- Refresh token
- Password
- JWT
- Session cookie
- Database credentials
- Long-lived authentication credentials

The QR code contains only a short-lived authentication challenge/reference.

Example conceptual payload:

    productivityos://auth?challenge=<opaque-one-time-value>

The challenge must be:

- Short-lived
- Single-use
- Bound to the authentication request
- Invalid after successful exchange
- Invalid after expiration

The exact challenge format is an implementation detail.

---

# 4. Web Side

The existing authenticated web application provides a way to generate an iOS login challenge.

Example:

    Connect iPhone

The web application requests:

    POST /auth/qr/challenge

The backend creates a temporary challenge.

The web application displays the resulting QR code.

The QR should communicate:

    Scan with Productivity OS

Do not display authentication tokens or sensitive information.

---

# 5. iOS Login Screen

When the iOS app does not have an authenticated session:

Display:

    Productivity OS

    Welcome back

    Scan the QR code
    from your Productivity OS account
    to continue.

            [ Scan QR ]

The design should follow the existing Productivity OS visual system.

The screen should feel:

- Clean
- Premium
- Minimal
- Native
- Secure

Do not implement registration.

Do not require email/password for the primary authentication flow.

---

# 6. QR Scanner

When the user taps:

    Scan QR

Request camera permission.

If permission has not been granted:

Explain why the camera is required.

Example:

    Camera Access Required

    Productivity OS uses your camera
    to securely connect this device
    to your account.

        [ Open Settings ]

If permission is granted:

Open the native SwiftUI camera scanning experience.

The scanner should:

- Clearly show the scanning area.
- Provide visual feedback when a QR is detected.
- Avoid scanning repeatedly.
- Stop scanning once a valid challenge is detected.

---

# 7. QR Validation

After scanning:

1. Extract the QR payload.
2. Validate that it belongs to Productivity OS.
3. Validate the expected authentication challenge format.
4. Reject malformed or unsupported QR codes.
5. Send the challenge to the backend.

Do not treat arbitrary QR URLs as authentication requests.

Invalid QR:

    This QR code isn't valid.

    Please scan the QR code
    generated by Productivity OS.

---

# 8. User Confirmation

After successfully reading a valid challenge, show a confirmation screen.

Example:

    Connect to Productivity OS?

    You're signing in to this
    iPhone with your Productivity OS account.

        [ Continue ]

        Cancel

Do not authenticate silently immediately after scanning.

The user must explicitly confirm the authentication.

---

# 9. Authentication Exchange

After confirmation:

    iOS
      ↓
    POST /auth/qr/exchange
      ↓
    Backend validates challenge
      ↓
    Backend verifies challenge ownership/state
      ↓
    Backend creates authenticated session
      ↓
    iOS receives authentication response

The exact endpoint and response must follow the backend implementation.

Do not invent the API contract if an existing implementation already exists.

---

# 10. Session Storage

After successful authentication:

Store credentials using the existing:

- KeychainManager
- AuthSession

Never store authentication credentials in:

- UserDefaults
- plaintext files
- application logs
- QR payloads

Update the global authentication state.

Navigate to:

    Today

---

# 11. Challenge Expiration

If the challenge has expired:

Display:

    This QR code has expired.

    Generate a new QR code
    and try again.

The user should be able to return to:

    Scan QR

No application restart should be required.

---

# 12. Challenge Already Used

If the backend reports that the challenge has already been used:

Display:

    This QR code is no longer available.

    Please generate a new QR code.

---

# 13. Cancellation

The user can cancel scanning.

Cancellation returns to the authentication screen.

No authentication state should change.

---

# 14. Network Failure

If the exchange fails because of connectivity:

Display:

    Unable to connect

    Check your internet connection
    and try again.

Provide:

    [ Try Again ]

The scanned challenge may be discarded and the user can scan again.

---

# 15. Authentication State

The application must use the existing authentication architecture.

Expected structure:

    App
     ↓
    AuthSession
     ↓
    ┌───────────────┐
    │ Authenticated │
    └───────┬───────┘
            ↓
           Today

    OR

    ┌────────────────┐
    │ Unauthenticated│
    └───────┬────────┘
            ↓
       QR Login

Do not duplicate authentication state inside the scanner.

---

# 16. App Launch

At application launch:

    Launch
      ↓
    Restore Keychain session
      ↓
    Authenticated?
      ├── Yes → Today
      └── No  → QR Login

Do not show QR Login briefly while restoring an existing valid session.

---

# 17. Existing Sessions

If an authenticated session already exists:

- Do not require QR scanning.
- Restore the session.
- Open Today.

QR authentication is primarily for initial device authentication.

---

# 18. SwiftUI Architecture

Recommended structure:

    LoginView
        ↓
    LoginViewModel
        ↓
    QRAuthenticationService
        ↓
    APIClient
        ↓
    Backend

Scanner:

    QRScannerView
        ↓
    QRScannerService

Authentication state:

    AuthSession
        ↓
    KeychainManager

The UI should not contain API calls.

The scanner should not own authentication state.

---

# 19. Camera Implementation

Use Apple's current native camera/scanning APIs appropriate for the project's deployment target.

Prefer:

- SwiftUI-native integration where practical.
- AVFoundation where required for camera scanning.
- Apple's native QR metadata detection.

Do not introduce a third-party QR scanning dependency unless the existing project already uses one or there is a concrete technical requirement.

---

# 20. Design

Use the existing Productivity OS DesignSystem:

- AppColors
- AppTypography
- AppSpacing
- AppButton
- existing animation tokens
- existing visual components

The scanner should visually match the Productivity OS application.

Recommended visual hierarchy:

    Branding
        ↓
    Explanation
        ↓
    Scan action
        ↓
    Camera experience

Avoid a generic "developer QR scanner" appearance.

---

# 21. Accessibility

Support:

- VoiceOver
- Camera permission explanation
- Accessible Scan QR button
- Accessible Continue button
- Accessible Cancel button
- Accessible error states

Important scanner information must not rely only on animation.

---

# 22. Privacy

The app should only use the camera while the scanner is active.

Stop camera capture when:

- QR is successfully detected
- user cancels
- screen disappears
- authentication succeeds

Do not store captured camera frames.

Do not upload camera images.

---

# 23. Testing

Test:

### Scanner

- camera permission granted
- camera permission denied
- valid Productivity OS QR
- invalid QR
- malformed QR
- duplicate detection prevention

### Authentication

- valid challenge
- expired challenge
- already-used challenge
- backend rejection
- network failure
- successful exchange

### Session

- Keychain persistence
- AuthSession update
- app restart
- authenticated launch
- unauthenticated launch

---

# 24. Acceptance Criteria

- [ ] Unauthenticated iOS app shows QR authentication.
- [ ] User can open the QR scanner.
- [ ] Camera permission is handled correctly.
- [ ] Valid Productivity OS QR is recognized.
- [ ] Invalid QR is rejected.
- [ ] User must explicitly confirm authentication.
- [ ] Challenge is exchanged with backend.
- [ ] Authentication credentials are securely stored.
- [ ] AuthSession becomes authenticated.
- [ ] User enters Today after successful authentication.
- [ ] Expired challenges are handled.
- [ ] Used challenges are handled.
- [ ] Network errors are handled.
- [ ] Camera stops after scanning/cancellation.
- [ ] No credentials are stored in the QR payload.
- [ ] No sensitive authentication data is logged.
- [ ] Existing Focus implementation remains unchanged.
- [ ] Tests pass.

---

# 25. Out of Scope

Do not implement:

- Registration
- Password login
- Forgot password
- Apple Sign In
- Google Sign In
- Live Activities
- Apple Watch authentication
- biometric authentication
- account switching
- QR-based authorization for arbitrary third-party apps

These may be considered in future milestones.
